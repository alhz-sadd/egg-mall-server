# AI协作与测试规范

为了避免在后续协作开发中反复出现“端口占用”、“代码语法报错”以及“由于表结构理解偏差导致的运行时 500 报错”，特制定本反思与改进规范。

## 1. 为什么会出现 npm run dev 报错 / 端口占用？

- **原因1：未正确释放端口**。AI在执行 `npm run dev` 检查服务是否能启动时，经常将服务挂在后台，但在告诉开发者“已完成”前，**忘记主动 kill 掉进程**。导致开发者自己手动去启动 `npm run dev` 时抛出 `EADDRINUSE 7001` 端口占用报错。
- **原因2：模板字符串语法错误**。AI在修改代码（如使用 SearchReplace 或 echo）时，偶尔会漏写反引号（`），导致抛出 `SyntaxError: missing ) after argument list`，从而导致整个 Node 服务直接启动失败（进程奔溃）。

## 2. 为什么会出现运行时 500 报错 (Unknown column)？

- **根本原因：想当然地假定表结构**。例如，最近的 `Unknown column 'operator.id' in 'field list'` 报错，是因为 AI 潜意识认为所有表的主键都是 `id`，以及旧版管理员表有 `real_name`，所以写了 `attributes: ['id', 'username', 'real_name']`。但实际上最新的 `sys_user` 表的主键是 `user_id`，展示名是 `nickname`。
- 这种“基于历史经验盲写代码”而不去 `sys_user.js` 模型中核对字段的习惯，导致只要接口一被调用，Sequelize 解析出的 SQL 就会直接报错挂掉。

## 3. 后续改进计划与 AI 强制执行流

从现在开始，AI 在进行任何新接口开发或代码修改时，**必须严格遵守以下工作流**：

### 3.1 字段与模型“核对制”
- 严禁凭空想象数据库表结构！
- 每次在写 `include` 关联查询、或 `where` 条件时，**必须先使用 Read 工具查看对应的 Model 文件**（如 `app/model/sys_user.js`），明确其 `primaryKey` 到底叫 `id` 还是 `user_id`，需要查询的字段到底叫 `real_name` 还是 `nickname`。

### 3.2 语法校验与后台自测机制
- 写完代码后，必须通过 `node -c app/service/xxx.js` 检查是否存在基本的语法错误。
- 也可以在后台静默启动 `npm run dev` 观察启动日志。如果启动失败，AI需**自行修复并重试**，不能将带有 `SyntaxError` 的代码抛给用户。

### 3.3 严禁私自常驻服务与释放端口的正确逻辑
- **禁止私自常驻运行服务**：AI 助手**不要**在每次修改代码后主动去执行 `npm run dev` 挂起服务，将启动服务的决定权交给开发者（用户会在自己的终端中运行）。
- **释放端口的正确逻辑**：只有当用户主动提出“启动报错”、“端口被占用”或明确要求“释放 7001”时，AI 助手才能去执行强制结束 7001 端口的命令，且**释放完成后，绝对不要自作主张再去帮用户启动 `npm run dev`，只需告诉用户端口已释放完毕即可**。
