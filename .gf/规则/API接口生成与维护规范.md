# API 接口文档生成与维护规范

为了规范化管理 `admin-inner` (A端平台)、`admin-outer` (B端商家) 和 `mobile` (C端用户) 三端的接口，并为后续清理废弃接口提供绝对依据，特制定本规范。

## 1. 目录结构与模块划分

所有接口文档统一存放在 `.gf/所有接口/` 目录下，并按照**业务模块**进行文件划分。

**文件模块划分与更新原则**：
在生成接口记录前，先检查目标目录下是否存在对应模块的 `.md` 文件。**如果没有就新建，如果有就修改/追加**。

已规划及常见的模块划分：
- `登录与基础.md` (包含登录、登出、获取用户信息、谷歌验证、菜单、角色分配等)
- `店铺管理.md` (包含店铺基本信息、店铺配置等)
- `业务员管理.md` (包含业务员增删改查、业务员业绩、充值配置等)
- `用户管理.md` (包含C端用户管理、实名认证、余额调整等)
- `充值提现方式.md` (包含充值提现渠道、渠道模板等)
- `充值.md` (包含充值请求、充值明细等)
- `提现.md` (包含提现请求、提现明细、提现参数配置等)
- `日志管理.md` (包含操作日志、登录日志等)
- `商品管理.md` (包含真实商品、商品分类等)
- `任务与任务商品.md` (包含任务商品管理、用户任务等)
- `订单管理.md` (包含C端订单等)
*(可根据实际业务功能扩展新建对应模块的 .md 文件)*

**端内接口归类规则**：
在每个模块的 `.md` 文件内，必须通过标题清晰地划分出三端的接口：
- **A端 (Admin-Inner)**：内部管理系统接口
- **B端 (Admin-Outer)**：商家管理系统接口
- **C端 (Mobile)**：移动端/H5端接口

## 2. 路由与请求前缀规范

所有接口的 Path 必须严格区分端，严禁混用：

- **Admin-Inner (平台端/A端)** 接口：强制统一以 `/api/admin-inner` 开头。
- **Admin-Outer (商家端/B端)** 接口：强制统一以 `/api/admin-outer` 开头。
- **Mobile (移动端/C端)** 接口：强制统一以 `/api/mobile` 开头。

## 3. 参数命名规范（核心强制）

- **数据库基准**：接口的入参（Query/Body）和出参（Response Data）**必须严格以数据库设计的字段为准**。
- **命名风格**：强制统一使用**蛇形命名法 (snake_case)**。例如必须使用 `user_id`, `shop_id`, `role_code`。
- **禁止项**：严禁在接口参数中混用驼峰命名法（如 `userId`, `shopId`），除非是第三方 SDK 的硬性规定。
- **一致性原则 (CRUD统一)**：针对同一业务主体（同一张数据表）的增、删、改、查系列接口，**必须保证其涉及的参数字段名称绝对一致**。例如 `POST` (创建) 和 `PUT` (更新) 接口若涉及相同的业务字段，字段命名与类型必须完全一致。如果后续维护中修改了其中某个接口的参数名称（如 `username` 改为 `user_name`），则**必须同步修改**同系列的其他接口以及对应 Markdown 文档，确保整个模块的数据字段对齐，以便降低后续维护成本。

## 4. 接口文档编写模板

每个接口在对应的模块 Markdown 文档中，必须按以下标准格式记录。

> **⚠️ 强制要求 (文档头部声明)**：
> **任何新建的模块 `.md` 文件，或在重构老文件时，必须在文档的最顶部（标题下方）声明以下内容**：
> 1. **核心业务声明与注意事项**：如哪些端不参与、权限隔离逻辑（如B端只能看本店）、复杂的联动逻辑（如审核通过要发奖金）等。
> 2. **涉及的数据表**：列出该模块业务所依赖的所有核心数据库表（如 `user_identity`, `customer_relation` 等），方便开发人员和 AI 快速定位关联表，防止遗漏 `include` 查询。

### [接口业务名称] (如：获取用户信息)

- **路径**: `GET /api/admin-outer/getUserInfo`
- **描述**: 获取当前登录用户的基本信息、角色及权限按钮标识集合。
- **请求头 (Headers)**:
  - `Authorization`: `Bearer <token>`
- **请求参数 (Query/Body)**:| 字段名   | 类型 | 必填  | 描述     |
  | -------- | ---- | ----- | -------- |
  | 示例字段 | int  | 是/否 | 示例描述 |
- **响应数据**:
  ```json
  {
    "code": 200,
    "message": "获取成功",
    "data": {
      "user_id": 1,
      "role_code": "shop_owner"
    }
  }
  ```

### [获取商户列表] (如：获取商户列表)

- **路径**: `GET /api/admin-inner/merchants`
- **描述**: 获取商户账号列表。
- **请求头 (Headers)**:
  - `Authorization`: `Bearer <token>`
- **请求参数 (Query)**:
  | 字段名   | 类型 | 必填  | 描述     |
  | -------- | ---- | ----- | -------- |
  | page     | int  | 否    | 页码     |
  | page_size| int  | 否    | 每页条数 |
  | role     | int  | 否    | 角色类型 |
- **响应数据**:
  ```json
  {
    "code": 200,
    "message": "获取成功",
    "data": {
      "list": [],
      "pagination": {}
    }
  }
  ```

### [获取店铺详情] (如：获取店铺详情)

- **路径**: `GET /api/admin-inner/shops/:id`
- **描述**: 获取店铺的详情资料。
- **请求头 (Headers)**:
  - `Authorization`: `Bearer <token>`
- **请求参数**: 无
- **响应数据**:
  ```json
  {
    "code": 200,
    "message": "获取成功",
    "data": {
      "shop_id": 1,
      "shop_name": "测试店铺",
      "config": {
        "config_id": 1
      }
    }
  }
  ```

## 5. 接口清理与废弃原则

- **白名单机制**：后续系统仅认可记录在 `.gf/所有接口/` 目录下的接口规范文档。
- **全新表结构专属原则 (抛弃老表)**：无论是 `admin-inner` (A端平台)、`admin-outer` (B端商家) 还是 `mobile` (C端用户)，**所有的接口业务逻辑必须彻底抛弃对老旧表结构的兼容**。三端的所有接口，**只允许维护和操作 `.gf/数据库.md` 中声明的新表结构**。**严禁在接口代码中执行向旧表同步数据或双写的逻辑**。老表已被标记为即将删除的废弃资产，一切数据交互均以 `.gf/数据库.md` 为唯一基准。
- **清理执行**：任何未在上述文档中记录的旧接口（例如历史遗留的 `/api/admin/xxx` 等杂乱路由），均被视为**无用/废弃接口**，将在后续的清理任务中被安全删除。

## 6. 编写说明要求

在每次创建、更新接口并写入对应模块的 Markdown 文档时，**必须在回复用户的总结中，明确说明是否还有该模块未补充完整的其他接口（比如没点到的/遗漏的接口）**。
如果有未涵盖但应当属于该模块的功能，**你需要主动根据功能逻辑在相应的文件中补全**，或者告知用户。
